# Performance port audit

This is a review record for the local `performance` branch. It does **not** prove
that every performance-related change was found or that the port has the same
behavior on a real device. It records what was checked and what remains open.

## Scope and method

- Base: `028a26319eae744d9c1ad90406624ae384a4c857` (`main`).
- Fixed source snapshot: `88e2a60562a5e6e7359ed93aa1a8b845e8ba7c18`
  (the `touch-the-wild` tip when this audit started). During the audit the
  branch ref was moved externally to its parent `81880286`; the fixed snapshot
  is also retained by `preserve/touch-the-wild-ahead-88e2a605` locally.
- Feature code reviewed through `b1453adf744cc28cf5372d468243949656415a6d`.
  The audit document and its scanner are later commits.
- Git reports 209 source commits, including 35 merges, in `main..88e2a605`.
  Commit subjects and changed paths were surveyed. A repeatable keyword scan
  produced 132 candidate commits. Relevant changes, mixed commits, and selected
  merge resolutions were inspected against the resulting code and `main`.
- The scanner compares every merge with **each** parent; this deliberately
  produces duplicate candidates from merged histories. It searches commit
  subjects and added/removed implementation and configuration lines. It skips
  documentation, test directories and Markdown diffs. Keywords can miss changes
  described differently, and a match can be unrelated. The complete content of
  every commit was not manually reviewed line by line.
- The local ref inventory was also checked for histories outside that snapshot.
  The pre-squash frame-generation backup `1fc27d2f` has identical
  `framegen.h`, `framegen_policy.h`, `framegen_capture.inc`, `framegen_metal.m`
  and `hle_nvn.c` files to the later squashed commit `73f75af7`; this does not
  establish equality of every file in those histories. The backup was not
  scanned commit-by-commit with the same method.
- Two independent upstream PR refs are outside the 209-commit snapshot:
  `upstream/pr-76` (`0f2a772c`) and `upstream/pr-303` (`127a2aa3`). Their
  purposes, clock algorithms, and diagnostic semantics were compared in the
  follow-up below; they were not imported wholesale. The 209-commit scan is
  therefore not a complete audit of every local ref.

Regenerate the candidate list from a checkout of this branch:

```sh
python3 dm/tools/performance_port_audit.py --output /tmp/nxnative-performance-scan.tsv
# Verify a source commit, including its parents:
git show --stat <source-commit>
git diff <parent-commit> <source-commit> -- <path>
# Inspect what the branch actually adds:
git diff 028a26319eae744d9c1ad90406624ae384a4c857 performance
```

The TSV lists each full source commit ID, its parent count, subject, changed
paths, keyword result and examples. It is a search index, not a classification
or proof of coverage. The table below records the manual classifications.

## Differences and exclusions

1. **Build scope conflict:** frame generation's separate HUD capture needs shader
   variants generated by `dmsh_build.py` and `dmsh_ui.py`. This branch changes
   those tools, `dmsh_chain.py`, and the generated `dmsh_chain.h`; it also changes
   a host Makefile dependency and test makefiles. The shader chain identifier
   changes for every game, so existing shader libraries need regeneration. This
   conflicts with a literal requirement of zero build-related changes. It is not
   the unrelated shader-build speed work excluded below.
2. `e0194d7c` makes Mac pipeline caches independent of `--save-copy` sessions.
   Its `scripts/run_mac.py --save-copy` workflow is absent from `main`; this
   exact behavior was **not ported**. The normal renderer does have pipeline
   caches, which does not establish equivalence for that workflow.
3. The source uses GPU generation names for device defaults. `2ed57968` uses a
   fixed set of iPhone model identifiers to avoid creating a Metal device before
   the performance HUD setting is applied. Unknown future models may receive
   different defaults.
4. The source's `DM_FILE_HEAP` backs a separate guest heap; `main` has the
   different whole-guest `DM_GUEST_FILE` mechanism. The branch uses `main`'s
   large or unaddressed transient-upload path and adds lazy GPU residency for
   low-memory CPU reads. It does not reproduce every source upload eligibility
   rule or prove the same memory footprint.
5. The render-pass optimization in `5ae13700` deliberately refuses some cases
   accepted by the source, including certain MetalFX, PSO, override and
   frame-generation UI cases. Its performance effect may therefore differ.
6. The source's settings-menu pause (`9b7d910b`) and FPS-counter layout changes
   associated with touch UI (`9cf78367`) are not carried as performance work.
   Seated/touch/widescreen features and their specialized optimizations, such as
   `b724b5a6`, `3dfa68b0`, `2395410b`, `ad79b24a`, are outside the requested
   scope. Independent shader-build and packaging optimizations, including
   `f90208a6`, `c024065f`, `e7de778f`, `f6c3b82b`, `839d3d45`, `0c2463ed` and
   the shader-build portion of `3c26c79d`, were excluded.

## Follow-up: upstream experiments and HUD capture

### PR #76: frame timing

Both implementations advance BOTW's game clock by elapsed time, but they are
not the same implementation. The PR permits target rates up to 240 fps; this
branch accepts verified custom rates from 20 to 120 in steps of 5, as well as
0, 30 and 60. The PR uses the last frame duration, caps one step at 50 ms,
and carries the remainder below its 1/240 s minimum. This branch averages five
samples, caps that average at 1/15 s, and resets the filter after a pause over
250 ms. Their behavior during a hitch is intentionally different.

For an identical synthetic 120-fps/144-Hz periodic sequence of 500 intervals,
actual time was 4.166667 s; this branch advanced 4.161111 s, including filter
warmup, and the PR advanced 4.166666 s. After a 200 ms stall and ten 60-Hz
intervals, actual time was 0.366667 s, this branch advanced 0.366667 s, and
PR #76 advanced 0.216667 s. These are calculations using the two algorithms,
not measurements from gameplay, and do not establish which looks better.

The comparison found a correctness hole: a game-controlled frame interval or
movie could leave the fractional clock active. `fe8af968` clears the guest's
latched fractional ratio while the game's override or movie flag is set, and
makes the host leave fractional timing until control returns. A native ARM64
test executes the actual emitted setter and four game-step stubs with and
without those flags, including a missing VFR object at startup. Link pacing and
frame-generation unit tests also pass. This does not prove a real cutscene's
speed or presentation without gameplay testing.

The branch now adopts the PR's physics floor during fractional stepping: the
game's own ratio, with a minimum of 0.5, yields at least three solver substeps.
At 120 real game frames per second this is three substeps instead of the six
previously forced by this branch; at 30 fps it remains six. Longer frames can
require more. The native ARM64 regression executes the emitted patch over the
floor, original-path and longer-frame cases. In a separate Unicorn run using
this branch's rewrite of the actual 1.9.0 executable, the game's own solver
setup stored 3, 3, 5, 6 and 9 steps at 120, 60, 40, 30 and 20 real fps;
with fractional timing inactive, a 0.25 ratio followed the original two-step path. To
repeat that last check, supply a rewritten game executable and its sibling
fixups/cuts tables to `python3 dm/tools/tests/research_botw_physics.py
<work-dir>/main.patched.bin` with Unicorn installed. Game files stay outside
Git. The PR notes that two substeps made ragdolls unstable; neither gameplay
stability nor a CPU/FPS improvement has been measured for this change on this
branch. The PR's independent
render-scale-above-1 feature expands the game's buffer pools and is not a frame
rate optimization; it was not imported as part of this comparison.

### PR #303: pool observation

`DM_NVN_POOLPEAK` records 64-KiB pool pages on which a texture has ever been
placed and reports the largest range never touched. The existing `DM_MEMSTAT`
reports process footprint and Metal allocation sizes; these are complementary,
not equivalent. PR #303 is an opt-in diagnostic, not itself an optimization.
Its 13 extracted tests pass. In an extra controlled example, two disjoint
four-page allocations at different times produce eight historical pages and
zero never-used pages although only four pages are live at once. The diagnostic
does not measure peak simultaneous live use. It was not imported; a future
pool diagnostic should name the historical-union metric clearly and handle
pool lifetimes and concurrency deliberately.

### HUD without a new shader-generation path

The readable-tile `_bf` shader variant already exists on `main`. A controlled
Metal probe specializes that existing variant to write one fragment result to
both a HUD attachment and a scene attachment, and uses Metal's
[`alphaToOneEnabled`](https://developer.apple.com/documentation/metal/mtlrenderpipelinedescriptor/isalphatooneenabled?language=objc)
to force only attachment 0's alpha to one. On this Apple M2 the probe read back
HUD alpha 255, scene alpha 64, and exactly 65,536 fragment invocations for a
256-by-256 draw. With the option off both alphas were 64. Reproduce it with:

```sh
MTL_DEBUG_LAYER=1 python3 dm/gfx/tests/research_framegen_hud.py
```

This tests a synthetic fragment through the existing `dmsh_fetch.fold` code
and the classic Metal API. It is not an integration test of the production
Metal 4 renderer, alpha-tested HUD, blending modes, or an iPhone/game.
An earlier color-attachment-map experiment had an invalid control and is
inconclusive; it is not evidence for or against another solution. Metal also
supports a [composited UI input](https://developer.apple.com/documentation/metalfx/mtlfxframeinterpolatorbase/uitexture),
but its visual equivalence to a separate HUD has not been established here.
Apple's [function-stitching API](https://developer.apple.com/videos/play/wwdc2021/10229/)
requires functions prepared with the `stitchable` attribute; the existing shader
generator does not emit such functions, so this is not an established way to
add a second output to already-built arbitrary fragment shaders.

Coverage is the main obstacle. A read-only survey of one *older* BOTW Mac
cache (`b-c2cc5a7544c5`, not the chain built by this branch) found 10,560 pixel
shaders: 6,414 with `_bf`, 10,318 with `_bui`, 6,268 with both, and 4,050
with `_bui` but no `_bf`. These are cache-wide counts, not a count of shaders
used by the HUD in any particular frame. Packaged apps do not generally carry
shader sources. Thus replacing `_bui` with existing `_bf` variants cannot yet
be shown to cover actual UI draws, alpha testing, blend state or all supported
configurations. Missing variants would require a safe fallback, and falling
back to the fully composited UI or skipping interpolation changes behavior.
The build-scope conflict in difference 1 above remains unresolved; **this
branch still contains the shader-generation changes**. Establish actual HUD
shader coverage on representative scenes and prove any fallback on the target
Metal 4 devices before replacing the current implementation.

## Evidence and limits

- Mac host builds passed; the most recent after the clock correction emitted
  59 warnings. This is a compile result, not a gameplay result.
- Frame-generation GPU tests passed, including 1,295 checks and twelve isolated
  controlled-motion processes; frame-rate and live scale state tests passed.
- BC GPU tests passed with native BC and forced fallback modes. The fallback was
  simulated on an M2 Mac; it was not checked on a phone lacking native BC.
- Low-memory GPU tests passed: `t_addr_known` 26 checks in each of two modes,
  `t_direct_upload` 26,384 checks, `t_pool_chunks` 146, and `t_vbuf` 115.
- Seven launcher/settings Python tests and 22 shader-chain/HUD-variant tests
  passed. iOS launcher sources built in a simulator test harness with two
  additional temporary linker stubs; the device `main.m` passed an iPhoneOS SDK
  syntax check. Neither is a complete production iOS build or physical-device run.
- No baseline-versus-candidate gameplay/FPS measurement, physical iPhone run,
  full shader-library rebuild, or five-game `scripts/regress.py check` was
  completed. The repository's regression harness can remove older shader caches
  by default; those existing caches were not removed for this audit.

To raise confidence further, resolve the build-scope conflict, reproduce the
scanner output, review remaining candidates by hand, rebuild the affected
shader libraries, run the required multi-game regression on isolated caches,
and compare the same gameplay route on the actual target devices with the same
settings and saves. Only those measurements can establish practical frame rate,
visual behavior, and memory use; even they cannot mathematically prove that no
unrecognized change was omitted.
